Chat view

A chat is another way to look at a terminal tab. The tab, its tmux window and its place in the workspace do not change. Only what fills the tab changes.

  • One column, 640px wide, centred. Your messages sit on the right in a bubble; the agent's text runs unboxed on the left, rendered as Markdown.
  • Tool calls are single rows that expand on click. File edits are rows too; clicking one opens that file in the Git diff tab.
  • The composer holds the model and effort pills, the context meter and Send. Send becomes Stop while the agent is working.
  • Status is unchanged. The Agents list, notifications and the tab's attention badge work as they do for terminal agents.
  • File links come from Markdown links and from inline code that is a path existing on the host. They show the file name and open the full path. Chat text has no terminal wrapping, so links are not cut short.

By the way

A side question that does not touch the main conversation. Claude answers one question in place and Codex forks the thread, so Muxflow takes over /btw and /side and handles them one way for both: fork the conversation and open the fork as a split beside the chat.

  • How you ask: type /btw or /side and the question. Muxflow's own entries replace the provider's in the slash list, for any provider that can fork.
  • What happens: Muxflow forks the conversation with the fork it already has ("Branch conversation"), opens it in a tmux split beside the chat, and sends your question as its first message.
  • It is a normal session. You can ask follow-ups, and it has its own row in the Agents list, titled with the original name and "(fork)", the same as a fork from the Branch button. It has the same permissions as the session it came from, and it is left out of History.
  • The main turn is not interrupted. The fork starts from the last finished reply.
  • On the phone there are no splits, so the fork opens as its own chat screen with a back arrow to the original.

Terminal mode or Chat mode

Agents still start from a terminal. You type claude, codex or your alias, and Muxflow detects the agent by its running process, as it does today. One setting decides what you get.

  • One mode for the host: Terminal or Chat, set in the desktop app's Settings. The default is Terminal.
  • No switching a session. A session is a terminal or a chat for its whole life.
  • Changing the mode affects agents started afterwards. Sessions already running stay as they are.
  • The phone follows the host. Its Settings shows the mode read-only and says to change it in the desktop app.
  • pi stays a terminal in both modes for now. Chat for pi is tracked as T066.

What happens when an agent starts in Chat mode

  • The pane restarts running the agent headless, before you have typed a prompt, so nothing is lost.
  • If you started it with a resume, such as claude -r, the chat opens on that conversation with its earlier messages.
  • The pane restarts with the agent's environment and directory, so a virtualenv or exported variables carry over. The original shell and its command history do not; closing the chat leaves a fresh shell in the pane.
  • Flags that only make sense in a terminal are dropped. Model, permission mode and extra directories carry over.

Details card

Chat sessions only. It floats at the top right of the chat area, and is not shown beside terminals.

  • Host and folder. Clicking the folder reveals it in the Files panel.
  • Branch. A menu of local branches with a filter. Switching runs a normal checkout; if Git refuses, the error is shown and nothing changes.
  • Commit… opens the Git panel's commit form.
  • Changes vs origin/main shows lines added and removed against the default branch, and opens the Git panel in that scope.
  • Context shows tokens used against the model's window.
  • Auto-hide. The card shows only when the chat area is at least 940px wide, so the 640px column and the card never overlap. Below that it is hidden and the Details button opens it as a popover.

Git view

An improvement to the existing Git view, for terminal and chat sessions alike. The Git panel stays as the file list. The diff it opens shows only the changed hunks, in one tab that is reused.

  • One diff tab. Clicking a file in the Git panel shows it in the same tab, the way file previews work, instead of opening another tab.
  • One file at a time, as in VS Code's source control. The tab shows the hunks of the file you clicked. Each hunk collapses, and Collapse all has a button and a shortcut.
  • Scope at the top of the Git panel: Uncommitted, or against origin/main. The panel lists the files for the scope you pick.
  • Hunks come from Git itself, with three lines of context, so staging or discarding a hunk acts on exactly what is shown. Those buttons appear only in the Uncommitted scope.
  • Show whole file opens today's full-file diff for that file.
  • "Only this session's changes" is not in this version. It needs per-session edit tracking and can follow once chat reports edits.

History

A searchable list of sessions Muxflow has seen on this host, It is an overlay, not a tab. Open it from the History button in the Agents header, from the command palette, or with a shortcut.

  • What is stored: provider, session id, the tab's latest title, workspace, folder and last activity. Up to 1,000 sessions in one JSON file on the host; the oldest drop off.
  • Search matches titles, workspace and provider, using the same fuzzy matching as Quick Open.
  • Enter focuses the session if it is still running. Otherwise it resumes it in a new tab in the workspace of the same name. If that workspace no longer exists, Muxflow creates it in the session's folder.
  • Forks made by /btw are left out of History.
  • Grouped: snoozed sessions first, each with its wake time and a Wake now button, then every other session by last activity.
  • Sessions that ran while the host helper was not running are not listed. Resuming from the shell still works for those.

Snooze

Snoozing closes the session, which frees its memory, and brings it back to your attention later. Closing a tab already keeps the session in History, so there is no separate Settle.

  • Where: the agent row's menu and the tab's menu.
  • When: the intervals are set in Settings. The defaults are in 1 hour, in 3 hours, tomorrow at 09:00 and Monday at 09:00, plus a time you pick.
  • At wake time the session reappears at the top of the Agents list with a "Woke" mark and a notification. Nothing starts until you click it; clicking resumes it.
  • Wake now is on each snoozed session at the top of History.
  • An agent that is working or blocked cannot be snoozed.

Phone

The phone renders the same chat data as the desktop. A chat session opens as chat; a terminal session opens as a terminal, as today.

  • Chat screen: messages, tool rows, permission and question cards, and a composer with slash commands.
  • Voice in a chat is a mode you turn on: the composer is replaced by the voice bar and replies are read aloud.
  • The Voice screen stays for terminal sessions, as today.
  • Details: a button in the header opens branch, changes and context as a sheet.
  • History and Snooze: a History screen with search, and Snooze in the long-press menu on an agent.
  • The protocol version is bumped. The phone app and the host release together, and an older app is told to update.

How it runs

tmux still owns every agent. A chat is a tmux pane running the agent headless instead of its terminal UI, and the host helper talks to that pane over a local socket.

tmux pane (Claude)

A Muxflow pipe runs the unmodified claude binary in its JSON mode and relays its input and output to a socket. The pipe knows nothing about the protocol.
socket

Host helper

Speaks each provider's protocol and turns it into one set of chat events: messages, tool calls, requests, usage, commands, models.
existing
link

Desktop and phone

Subscribe to one chat and render it. They send messages, answers, Stop, rewind and model changes back.

tmux pane (Codex)

codex app-server listening on a socket. No pipe needed. One server per chat pane, so status is attributed to the right pane.
socket

Same host helper

If the helper restarts or updates, the panes keep running. The new helper finds them by a tag on the pane and reconnects.

Working, blocked and idle still come from the same hooks, so the Agents list and notifications need no second pipeline.

Adding another agent

Everything is shared except one provider module per agent. The host already keeps a table of agents for launch, resume and fork; chat extends that same table.

  • What a provider supplies: the command that runs it headless in a pane, a translation from its messages into Muxflow's chat events, a translation of send, stop, answer, rewind and model changes back into its protocol, and a way to load earlier messages.
  • What it declares: a capability list, such as rewind, sending mid-turn, model and effort choice, questions, and whether it can fork. The desktop and phone show or hide controls from that list, so an agent without rewind simply has no Edit button.
  • What is never repeated: the pipe, pane tagging, reconnect after a helper restart, the wire messages, and both chat UIs.
  • One shared test set. Every provider runs the same tests against recorded sessions, so a new agent is checked the same way as Claude and Codex.
  • Many agents at once. Several agents speak the Agent Client Protocol; Orca uses it for seven of them. One provider for that protocol would cover all of them. pi has its own JSON mode and would be a separate, small provider (T066).

Staying inside Anthropic's terms

  • The installed claude binary runs unmodified, with the login you already did in it.
  • Muxflow never reads, copies or stores its credentials, and never calls Anthropic's API itself.
  • The feature is not named after Claude Code and uses none of its branding.
  • I still recommend asking Anthropic to confirm this use before the chat ships to other users.

Manual QA, once, at the end

One run through the real app against the devbox host, driven by a fresh agent that only reports what it sees:

  1. Set the host to Chat mode. Open a terminal and type your claude alias. The tab becomes a chat.
  2. Ask for a file edit in Auto mode. An edit row appears; clicking it opens that file's hunks in the Git diff tab.
  3. Start a long turn and press Stop. The agent goes idle.
  4. Edit the first message and resend. Everything after it is gone and the new reply follows.
  5. Type / and confirm a skill installed on the host is listed.
  6. Restart the host helper mid-turn. The chat reconnects and the turn finishes.
  7. Ask a /btw question mid-turn. A fork opens in a split and the main turn keeps running.
  8. Repeat steps 1 to 4 with codex.
  9. Close the tab, find the session in History, resume it. Snooze it for one minute and confirm it wakes as a placeholder.
  10. Set the host back to Terminal mode. A new claude starts as a terminal, and the running chat is unaffected.
