# Muxflow Mobile — design document

Status: approved scope, ready to implement. Owner: Maintainer. Target: Android first.

This document is written to be executed literally. Every screen, request,
string, and state transition is spelled out. Where the document says
"verify against X", the engineer runs or reads X before relying on the
statement. Where a decision is not in this document, choose the option
that touches the least code and write the decision down in
`docs/mobile/decisions.md`.

---

## 1. Summary

Muxflow Mobile is an Android app that connects to an existing Muxflow host
over SSH, exactly the way the desktop does, and lets you:

1. see which agents (Codex / Claude Code) exist and whether any of them are
   blocked waiting for you;
2. open an agent's terminal, read what it is doing, and type a short reply;
3. browse the files under that agent's working directory and read Markdown
   files (plans, notes) rendered nicely;
4. get an Android notification when an agent becomes **blocked** or
   **completes**, even when the app is in the background;
5. start a new agent the way you would in a terminal: open a new shell
   window in an existing workspace and type `claude` or `codex`. The app
   has no agent launcher of its own; every tmux window is an interactive
   terminal (§9.4 → §9.5), and one row creates a fresh window.

That is the whole product for v1.

### Non-goals (do not build these)

- iOS (structure the code so it is possible later, but do not test on iOS).
- Split panes, pane layout, zoom, resizing tmux, creating/renaming/closing
  sessions, windows, or panes.
- Creating workspaces (tmux sessions); any agent launcher UI; resuming or
  renaming agents; installing agent hooks; installing or upgrading the
  `muxflow-host` helper.
- Editing files, creating files, uploads, downloads, Git of any kind.
  Text only, in both directions: the terminal accepts typed/pasted **text**
  and nothing else — no image paste, no file share-sheet target, no
  terminal upload (`OPERATION_PREPARE_TERMINAL_UPLOAD` and friends are never
  sent), no saving remote files to the phone.
  *Deviation (voice mode, §9.11, 2026-09):* the phone also records speech and
  plays back synthesized replies. What crosses into the terminal is still
  text: the host returns a one-line transcript and the phone types it with
  the ordinary `TERMINAL_INPUT`; the reply audio is a push the phone only
  plays. No file transfer, no share target, no saving.
- Multiple simultaneous hosts. One host is connected at a time.
- Push notifications through any cloud service. Notifications are local,
  generated by the app's own long-lived SSH connection.
- A full soft-keyboard terminal emulator experience (no ctrl/alt modifier
  keyboard or general pointer/button input). A text field plus the key chips is
  the entire typing surface. Terminal-specific touch is limited to scrolling,
  link/path taps, and explicit selection/Copy. A swipe over an alternate-screen
  TUI is translated to its wheel input so its own history remains reachable; it
  does not turn the terminal WebView into a general input field.

## 2. Decisions that are fixed

| # | Decision | Why |
| --- | --- | --- |
| D1 | Transport is **SSH** from the phone, running `$HOME/.local/bin/muxflow-host bridge --stdio` on the host, identical to the desktop. No new host code, no TCP listener. | Reuses the existing daemon, protocol, hooks and security model. The user already uses SSH from the phone (Termux) and it works. |
| D2 | Stack: **Expo (React Native) + TypeScript**, using an Expo **development build** (not Expo Go), with one custom **Expo Module written in Kotlin** that wraps the `sshj` SSH library. | Expo Go cannot ship native SSH. Everything above the SSH byte pipe stays in TypeScript so the protocol client is written once. |
| D3 | Terminal rendering: **xterm.js inside a `react-native-webview`**, fed the same byte stream the desktop feeds its xterm. | The host already produces xterm-ready bytes (seed + output). Re-implementing a VT parser natively is out of scope. |
| D4 | Markdown rendering: `marked` + `DOMPurify` inside a WebView, using the desktop's `renderSafeMarkdown` rules (§11.2) copied verbatim. | Same sanitiser as the desktop; a Markdown file that renders on desktop renders the same on the phone. |
| D5 | Protocol messages are decoded with `@bufbuild/protobuf` code generated from `crates/protocol/proto/envelope.proto`. The `.proto` file is the only source of truth; never hand-write message shapes. | The desktop and host both generate from this file. |
| D6 | A side **takes** the tmux window size only while a person is using it there, and nobody releases. The phone takes when its terminal opens, on rotation and keyboard show/hide, and on input while the window is not at its size; the desktop takes on a keystroke or pointer-down while the window is not at its size — never on window focus, never idle. Both rate-limit to one take per 2 s. A take is the host's existing resize: `refresh-client -C` then `switch-client -E` when another client shares the session (`terminal.rs::resize`, `claim_latest`); tmux's `window-size latest` does the rest. Verified on tmux 3.5a: a size request or input alone never makes a control client `latest`, a silent attached client loses to a take, and a killed client releases on its own. | Agents redraw their TUI at phone width, which is the only way the terminal is readable, and the laptop gets its width back the moment it is used — no dialog, no setting, no release message. A phone left open in a pocket cannot drift back into control. |
| D6b | The terminal is the control plane, for v1 and beyond. No transcript parsing, screen scraping, or keystroke choreography behind buttons. A future read-only "Conversation" view (for voice or skimming) would tail the agents' own transcript files through the file service — reading, never controlling. | Earlier agent tools ended up with the terminal as the default and tens of thousands of lines of fragile per-vendor keystroke logic around their structured views. |
| D7 | Attention state (`seen_generation`) is shared with the desktop through the host. Opening an agent on the phone clears its badge on the desktop and vice-versa. | It is free: the host already owns this state. |
| D8 | Authentication is SSH **public key only**, with a key pair generated on the phone and stored in Android-encrypted storage. Host key trust is trust-on-first-use with a fingerprint confirmation. | Matches how the user already uses SSH. No passwords stored on the phone. |
| D9 | Background delivery of notifications uses an Android **foreground service** that keeps the app process (and its SSH connection) alive, with a persistent "Connected to <host>" notification. | The only way to get "agent is blocked" on the lock screen without a push server. |
| D10 | Package/app id: `dev.muxflow.mobile`. App display name: `Muxflow`. Source lives in this repository under `apps/mobile`. | One repo, one `.proto`, one release process. |

```
│  │ router)  │ │             │ │ (§7)     │ │                │  │
│  └────┬─────┘ └──────┬──────┘ └────┬─────┘ └───────┬────────┘  │
│       │ WebView      │             │ bytes         │            │
│  ┌────┴─────┐        │      ┌──────┴───────┐       │            │
│  │ xterm.js │        └──────┤ MuxflowSsh   ├───────┘            │
│  │ marked   │               │ Expo Module  │ (Kotlin, sshj)     │
│  └──────────┘               └──────┬───────┘                    │
│                      Foreground service keeps process alive     │
└────────────────────────────────────┼────────────────────────────┘
                                     │ SSH (port 22), exec channel
┌────────────────────────────────────┼─────────────── host ───────┐
│  $HOME/.local/bin/muxflow-host bridge --stdio                    │
│         │ private Unix socket                                   │
│  muxflow-host daemon  ──  tmux control mode  ──  tmux server    │
│         ▲ hooks (Codex / Claude Code lifecycle)                 │
└─────────────────────────────────────────────────────────────────┘
```

Facts about the host side the engineer must not re-derive (read
`apps/host/src/main.rs`, `apps/host/src/bridge.rs`,
`apps/desktop/src-tauri/src/connection/transport.rs` to confirm):

- The desktop runs, over SSH, exactly the command string
  `$HOME/.local/bin/muxflow-host bridge --stdio`. The bridge connects to the
  daemon's Unix socket, **auto-starting the daemon if it is not running**,
  and pumps stdin/stdout to it. Stdin closing tears the connection down.
- The desktop's ssh options are `-T`, `-o BatchMode=yes`,
  `-o ServerAliveInterval=15`, `-o ServerAliveCountMax=3`,
  `-o ConnectTimeout=10`, `-o Compression=yes`, `-o IPQoS=lowdelay`. The phone
  reproduces the keepalive (15 s, 3 misses), the connect timeout and
  compression through sshj settings.
- The helper must already be installed by the desktop. The phone does not
  install it.
- The executable stays at `$HOME/.local/bin/muxflow-host`. Its one production
  Unix socket is `/tmp/muxflow-<uid>/host.sock` on Linux and macOS, independent
  of XDG/TMPDIR shell variables. Durable agent state, pins, ordering and queued
  hook events live under `$HOME/.local/state/muxflow` on Linux and
  `$HOME/Library/Application Support/dev.muxflow.desktop` on macOS.
- File bodies are served only on a **bulk connection** — a second
  `bridge --stdio` exec channel handshaken with `bulkConnection: true`
  (§11.1). The control channel refuses `OPEN_FILE_STREAM` with
  `bulk_connection_required` (`apps/host/src/service/requests/operation_policy.rs`,
  `Lane::Bulk`). The native module therefore has to open two exec channels on
  one SSH session.

## 6. Native module: `muxflow-ssh` (Kotlin, sshj)

The module is deliberately dumb: it opens an SSH exec channel and moves
bytes. It knows nothing about the protocol.

### 6.1 TypeScript API (`src/ssh/MuxflowSsh.ts`)

```ts
export interface SshTarget {
  host: string;          // hostname or IP, as typed by the user
  port: number;          // default 22
  user: string;
}

export type SshEvent =
  | { type: "hostKey"; connectionId: string; algorithm: string; fingerprintSha256: string } // emitted only when the key is not yet trusted
  | { type: "connected"; connectionId: string }
  | { type: "data"; connectionId: string; base64: string }          // stdout bytes from the remote command
  | { type: "stderr"; connectionId: string; text: string }          // stderr text, utf-8, for diagnostics only
  | { type: "closed"; connectionId: string; exitCode: number | null; reason: string };

export interface MuxflowSsh {
  generateKeyPair(): Promise<{ publicKeyOpenSsh: string }>;     // ed25519; private key never leaves native storage
  getPublicKey(): Promise<string | null>;                        // "ssh-ed25519 AAAA... muxflow-mobile"
  deleteKeyPair(): Promise<void>;
  connect(connectionId: string, target: SshTarget, command: string, trustedHostKeyFingerprint: string | null): Promise<void>;
  trustHostKey(connectionId: string, fingerprintSha256: string): Promise<void>; // answers a "hostKey" event
  write(connectionId: string, base64: string): Promise<void>;   // stdin bytes to the remote command
  close(connectionId: string): Promise<void>;
  startForegroundService(title: string, body: string): Promise<void>;
  stopForegroundService(): Promise<void>;
  setServiceNotification(title: string, body: string): Promise<void>; // text for the next auto-start; re-posted in place while running
  addListener(listener: (event: SshEvent) => void): () => void;
  addDisconnectListener(listener: () => void): () => void;      // the notification's Disconnect action
  scheduleWake(token: string, delayMs: number): Promise<void>;  // a native clock; answers through addWakeListener
  cancelWake(token: string): Promise<void>;
  addWakeListener(listener: (token: string) => void): () => void;
}
```

### 6.2 Behaviour, exactly

- `generateKeyPair` creates an ed25519 key with Bouncy Castle, stores the
  private key PEM in `EncryptedSharedPreferences` (key alias
  `muxflow.ssh.private`), and returns the OpenSSH public line with comment
  `muxflow-mobile`. Calling it when a key exists **replaces** the key; the
  UI confirms first (§9.1).
- `connect`:
  1. Creates an `SSHClient`, sets `setConnectTimeout(10_000)`,
     `setTimeout(0)`, keepalive `KeepAliveProvider.KEEP_ALIVE` with interval
     15 s, and `getConnection().setMaxPacketSize` default. Enables zlib
     compression (`useCompression()`).
  2. Installs a `HostKeyVerifier`. If `trustedHostKeyFingerprint` is null or
     differs from the presented key: when null, emit `hostKey` and **block
     the verifier** until `trustHostKey` is called for that connectionId
     (or 60 s pass → reject, close with reason `"hostKeyNotTrusted"`).
     When non-null and different, reject immediately and close with
     reason `"hostKeyMismatch"`.
  3. Authenticates with `auth(user, [none, publickey])` — the OpenSSH
     client's order. `none` first: a Tailscale SSH host has already
     authenticated the phone by its tailnet identity and accepts it, so no
     key on the phone is required (Termux-style `ssh host` just works). A
     regular sshd answers `none` with its accepted methods and sshj moves on
     to `publickey` with the stored key, if any. Failure → close with
     reason `"authFailed"`. Tailscale check mode delivers its sign-in URL as
     an auth banner and holds the login open until approved; v1 does not
     surface the banner.
  4. Opens a session, **does not** request a PTY, runs `exec(command)`.
     Emits `connected` once the command is running.
  5. Pumps the command's stdout to `data` events in chunks of at most
     64 KiB, base64-encoded. Pumps stderr to `stderr` events line by line.
  6. On command exit or transport failure, emits `closed` with the exit code
     (127 means the helper is missing — §12 maps this to a user message)
     and a reason string from the set
     `hostKeyNotTrusted | hostKeyMismatch | authFailed | connectFailed | exited | closedByClient | networkLost`.
- `write` writes the bytes to the channel's stdin and flushes. The
  TypeScript side serialises writes (one in flight at a time, queued).
- `close` closes stdin, then the channel, then the client. Idempotent.
- The module runs all network work on a dedicated thread per connection.
  Events are delivered on the JS thread via Expo's `sendEvent`.
- `scheduleWake(token, delayMs)` posts a runnable to a `Handler` on the main
  looper and, when it runs, emits the module's second event, `onWake`, with
  `{ token }`. `cancelWake(token)` removes the runnable; a token that is not
  pending is a no-op, and scheduling a pending token again replaces its
  deadline. This is the clock behind `src/session/backgroundTimer.ts`:
  React Native freezes every JS timer while the activity is paused
  (`JavaTimerManager.onHostPause`), a `Handler` does not, and native → JS
  events are delivered in the background. The `BackgroundTimer` keys each
  callback by a monotonic token, so a wake for a cleared timer runs nothing.

### 6.3 Foreground service (`ConnectionService.kt`)

- A `Service` started with `startForegroundService`, declared with
  `android:foregroundServiceType="specialUse"` and
  `PROPERTY_SPECIAL_USE_FGS_SUBTYPE = "Persistent SSH session that delivers agent status notifications"`.
  Permissions in the manifest: `INTERNET`, `FOREGROUND_SERVICE`,
  `FOREGROUND_SERVICE_SPECIAL_USE`, `POST_NOTIFICATIONS`,
  `RECEIVE_BOOT_COMPLETED` is **not** requested (no auto-start on boot).
- The service posts one ongoing notification on channel
  `connection` (importance LOW, no sound): title = the `title` argument,
  body = the `body` argument, one action "Disconnect". The app keeps the
  text with `setServiceNotification`: title `"Muxflow"`, body
  `"Connected to <host label>"` while the control connection is up and
  `"Reconnecting to <host label>"` while §7.2 is re-dialling it. The
  module stores the last text for the next automatic start and, while the
  service is running, re-posts the notification under the same id
  (`ConnectionService.update`, a plain `notify`) — never a service start,
  which Android 12+ may refuse from the background.
- Tapping "Disconnect" emits the module's third event,
  `onDisconnectRequested` (`addDisconnectListener`), **before** anything is
  closed and whether or not a channel is open; then every open channel is
  closed (`closed` with reason `closedByClient`) and the service stops. The
  event is what the app acts on — `disconnectHost()`, the same path as the
  in-app Disconnect, which also cancels a pending §7.2 backoff. Between
  attempts there is no channel, so `closedByClient` alone could not reach
  JavaScript, and the native timer would keep dialling with the service gone.
- The service holds a partial wake lock while it runs. The TypeScript
  `HostConnection` (§7) lives in the app's normal JS runtime; the service
  exists only so Android does not kill that runtime. Do not put protocol
  logic in Kotlin.
- The service is started when a connection reaches `connected` and
  stopped when the user disconnects or the connection ends with a
  non-retryable reason.

## 7. Protocol client (`src/protocol/HostConnection.ts`)

### 7.1 Framing

Every message in both directions is one **frame**: a 4-byte big-endian
unsigned length followed by that many bytes of a protobuf-encoded
`tmux_agent.protocol.v1.Envelope`. Maximum body length is
`16 * 1024 * 1024` bytes; a larger length is a protocol error and the
connection is closed. Reference implementation:
`crates/protocol/src/lib.rs` (`encode_frame`, `FrameAccumulator`). Port
`FrameAccumulator` to TypeScript one-to-one and unit test it with split
chunks, empty chunks, and two frames in one chunk.

Every `Envelope` the app sends carries the generated `protocolMajor` (currently 3).
The `requestId` is a per-connection counter starting
at 1. `sequence`, `streamId`, `priority` are left at 0 for everything this
app sends.

### 7.2 Connection state machine

```
idle ──connect()──▶ sshConnecting ──(ssh connected)──▶ handshaking
   ▲                    │ hostKey event → awaitingHostKeyTrust ─trust─▶ (continues)
   │                    │ closed
   │                    ▼
   ├── failed(reason) ◀─┘
   │
   │  handshaking ──(ServerHello ok + Subscribe response ok)──▶ connected
   │       │ protocol-major mismatch
   │       ▼
   ├── incompatible(message)
   │
   │  connected ──closed(networkLost|exited)──▶ reconnecting(attempt n) ──▶ sshConnecting
   │  connected ──disconnect()──▶ idle
   └──────────────────────────────────────────────────────────────────────
```

Reconnect policy: on `closed` with reason `networkLost`, `exited`, or
`connectFailed` (the host unreachable on a retry, §12) while the user has
not tapped Disconnect, wait `min(2^n, 30)` seconds (n = 0,1,2,…) and
reconnect. Reset n to 0 after a connection has been `connected` for 60 s.
A handshake that gets no ServerHello or Subscribe response within 20 s is
treated like `exited`. After any `closed` with reason `authFailed`,
`hostKeyMismatch`, `hostKeyNotTrusted`, or exit code 127, go to `failed`
and do not retry.

Every reconnect is a brand-new connection: new `connectionEpoch` (§7.3),
full snapshot, and every open terminal re-attaches (§7.6).

The backoff, the handshake deadline and the 60 s stable timer run on the
native timer (`HostConnectionOptions.reconnectTimer`, `backgroundTimer()` in
the app; §6.2 `scheduleWake`), not `setTimeout`: React Native freezes JS
timers while the app is in the background, which is exactly where a link
dropped under the foreground service has to come back — where the handshake
that reconnect starts has to be given up on if the bridge never answers, and
where a connection that stays up for 60 s has to count as stable, or a phone
flapping in the background climbs to the 30 s cap and never comes down. The
request timers stay on `setTimeout`: not worth a bridge call per request.

### 7.3 Handshake (copied from `apps/desktop/src-tauri/src/connection/bridge.rs::handshake_and_snapshot`)

Immediately after the SSH `connected` event, send two frames without
waiting between them:

1. `Envelope{ requestId: 1, clientHello: { bulkConnection: false, connectionEpoch: <epoch> } }`
   - `protocolMajor` comes from the generated Rust contract at
     `apps/mobile/src/protocol/gen/host_contract.json`.
   - Mobile releases independently; both peers reject a different protocol
     major. Desktop and host are shipped together. There is no capability
     negotiation or read-only connection mode.
   - `connectionEpoch` is a counter persisted per saved host, incremented
     on every connection attempt.
2. `Envelope{ requestId: 2, request: { operation: OPERATION_SUBSCRIBE, scope: "full" } }`

Then read frames:

- Check the envelope's protocol major against the generated contract (currently
  3). A mismatch closes the connection as `incompatible`, with the message
  `"This host's Muxflow helper speaks protocol v{n}; this app needs v3. Update the app or the helper from Muxflow desktop."`
- The first payload must be `serverHello` (its `requestId` echoes the
  ClientHello's, 1, and `serverHello.connectionEpoch` echoes ours).
  An `error` payload closes the connection as `failed` with its display
  message; any other payload fails with `"host did not return ServerHello"`.
  The host rejects contract or bulk-identity mismatches before serving requests.
- A control hello must advertise positive terminal output byte and record
  windows; absent flow control fails admission.
- Store `serverHello.serverIdentity`, `terminalOutputWindowBytes`,
  `terminalOutputWindowRecords`, `helperVersion`, `helperBuildDigest`,
  `tmuxVersion`. The bridge already requires the daemon's exact SHA-256 build
  digest to match its own before it forwards this hello.
- Next, read until the frame with `requestId === 2` and a `response` payload.
  Frames with other payloads that arrive before it are buffered in order and
  processed after it — **except** event frames whose `sequence` is at or
  below `response.acceptedSequence`, which are dropped: the snapshot already
  incorporates them, and replaying one would read as a gap (verified against
  the host — the first topology reconcile routinely reaches stdout before the
  Subscribe response; the desktop does the same in
  `bridge.rs::event_follows_snapshot_barrier`). If `response.ok === false` →
  `failed("{errorCode}: {displayMessage}")`.
  `response.snapshot` is the full topology + agents snapshot; apply it (§8).
  `response.acceptedSequence` becomes the event watermark (§7.4).
  If `response.snapshot.serverIdentity !== serverHello.serverIdentity` → failed.
- State becomes `connected`. The foreground service is not started from
  here: the native module starts it on its own when the channel reaches SSH
  `connected` (§6.3), and the app only keeps its text current with
  `setServiceNotification` — `"Connected to {host label}"` now, and
  `"Reconnecting to {host label}"` while §7.2 re-dials.

### 7.4 Ordered events

Every `HostEvent` arrives in an `Envelope` whose `sequence` field is either
0 or the next ordered number. Keep `lastSequence`, initialised from the
Subscribe response's `acceptedSequence`. For every event frame:

- if `sequence === 0`: process it (it consumed no sequence number);
- else if `sequence === lastSequence + 1`: process, set `lastSequence`;
- else (gap or duplicate): log `protocol.gap {expected, got}` and
  **reconnect** (§7.2). The desktop uses a resync operation instead; the
  phone deliberately does the simpler thing.

Event handling by `HostEvent.kind`:

| kind | action |
| --- | --- |
| `TOPOLOGY_SNAPSHOT` | replace sessions/windows/panes in the store from `event.snapshot`; if `snapshot.agents` is present and `authoritative`, replace agents too. |
| `TOPOLOGY_DIRTY` | ignore (a snapshot follows). |
| `RESYNC_REQUIRED` | reconnect. |
| `TERMINAL_SEED` | deliver to the terminal attached to `event.terminal.paneId` as a **seed** (§7.6). Charge credit (§7.7). |
| `TERMINAL_OUTPUT` | deliver to that terminal as **output**. Charge credit. |
| `TERMINAL_EXIT` | `event.scope` is a **session id** (`"$N"`): the host's only emitter is `service.rs::reconcile_terminal_clients_locked`, when that session's control client failed. Mark every open terminal of that session as exited; show the banner in §9.5. |
| `TERMINAL_FLOW_PAUSED`, `TERMINAL_FLOW_STALLED` | ignore in v1 (the host recovers by itself; a stalled pane shows nothing until re-attached). |
| `TERMINAL_RESNAPSHOT_REQUIRED` | send `OPERATION_REQUEST_TERMINAL_SEED` for the pane in `event.scope` (§7.5). |
| `PANE_RESOURCE` | if `paneResource.requiresSeed` and that pane is `focusedPaneId` → send `OPERATION_REQUEST_TERMINAL_SEED`. Otherwise ignore. Charge credit (§7.7): the host charges the recovery bytes a visibility change admits on this event. Note that `REQUEST_TERMINAL_SEED` is itself a reveal (`terminal.rs::request_seed_for_render` forces the pane visible), which is why §7.6 step 4 clears `focusedPaneId` before hiding. |
| `TERMINAL_SEED_DIAGNOSTIC` | log `event.detail`. |
| `AGENT_STATE` | apply `event.agent` (§8.2), run the notification decision (§13). |
| `ACTIVE_ROOT`, `DIRECTORY_SNAPSHOT`, `FILE_CHANGED` | forward to the files feature if a browser is open for that root (§11.1); otherwise ignore. |
| `TERMINAL_CLIPBOARD_WRITE` | ignore in v1. |
| anything else | ignore, log the kind. |

Frames with an `error` payload and `requestId === 0` are connection-level
errors: show `displayMessage` as a toast; if `retryable === false`,
reconnect.

### 7.5 Requests this app sends (`src/protocol/requests.ts`)

All requests are `Envelope{ requestId, request: {...} }`. The client keeps a
map `requestId → { resolve, reject, timeoutHandle }`; a `response` frame
with a matching id settles it. Timeout is 20 s for everything except file
streams (60 s). A missed deadline fails only its request; the lane is torn
down (and §7.2 reconnects) only after three unanswered requests in a row
*and* 15 s without any answer — a slow link answers late, a stalled lane
never (desktop `connection.rs`, `docs/bugs/slow-link.md`). A `stale_topology`
refusal is retried once after waiting up to 1 s for the newer snapshot
(returns as soon as it lands). A `response` with `ok === false` rejects with
`HostError{ code: errorCode, message: displayMessage }`.

### 7.6 Terminal attach lifecycle

For one pane displayed on the Terminal screen (§9.5):

1. On screen mount, in this order: set `focusedPaneId`,
   `selectTerminalSession(sessionId)`, `resizeTerminal(cols, rows)` with the
   size measured by the WebView (§9.5), then `attachTerminal(sessionId, paneId)`.
   The select must precede the resize: the host sizes the *selected* session's
   control client and refuses a resize before one exists (verified live —
   `terminal_resize_rejected: no visible session control client`). The
   attach mounts the pane and makes it visible; it is followed at once by
   `requestTerminalSeed(paneId)`, which is what produces the `TERMINAL_SEED`
   event. A session whose control client already exists (selected earlier,
   or the window was just created) commits the pane without a capture, and
   flipping it visible captures nothing either — the desktop always follows
   its mount with an explicit reveal, and this is the phone's. The request is
   idempotent: a capture already in flight for a fresh attachment coalesces
   it. A `setTerminalVisibility(paneId, true)` after that is accepted but
   produces no second seed, so it is not sent on mount. The seed bytes are a
   complete xterm-ready stream for the *screen only* (screen contents, cursor
   position, modes — deliberately no scrollback, ~10 KB instead of ~190 KB)
   produced by `apps/host/src/service/terminal/seed.rs`. The client:
   `term.reset()`, then `term.write(seedBytes)`. Scrollback loads on demand —
   §7.6.1.
2. Every `TERMINAL_OUTPUT` for that pane: `term.write(bytes)` in arrival
   order. Track `generation` from `TerminalBytes.generation`; if a seed
   arrives with a generation lower than the last output written, discard
   the seed (stale).
3. If no seed arrives within 5 s of attach: send `requestTerminalSeed(paneId)`
   once; if still nothing after another 5 s show the "No output yet" hint
   (§9.5 states).
4. On screen unmount (back, or switching to Files): first clear
   `focusedPaneId`, then `setTerminalVisibility(paneId, false, { terminalEpoch: connectionEpoch, generationCutoff })`
   with empty `data`. The order matters: the hide answers with a
   `PANE_RESOURCE{ state: RELEASED, requiresSeed: true }` event, and §7.4 would
   turn that into a `REQUEST_TERMINAL_SEED` — a reveal — if the pane were still
   focused. Because the phone sends no serialized snapshot, the host cannot
   buffer the pane (`HiddenBuffered`); it *releases* it
   (`recovery_reason: "renderer handoff omitted a recoverable snapshot"`),
   delivers no output while hidden, and reseeds on the next reveal or attach
   (step 1). The reseed contains output produced while hidden (verified live).
5. On reconnect while the screen is mounted: run step 1 again — but only
   while the app is in the foreground (`AppState` not `background`). The
   whole step waits, not just the resize: `SELECT_TERMINAL_SESSION` alone
   takes the host's fresh, unsized control client out of `ignore-size`, and
   tmux would size the windows from its 80x24 default. A phone in a pocket
   with the screen left open must not touch the laptop's windows on a Wi-Fi
   flap. The deferred step 1 runs when the app returns to the foreground
   (one `AppState` listener).
6. On rotation or keyboard show/hide: re-measure and send
   `resizeTerminal(cols, rows)` again (debounced 150 ms), again only in the
   foreground. The host emits a `TERMINAL_RESNAPSHOT_REQUIRED` or a new seed;
   handle as §7.4.
7. Nothing is sent on unmount; the laptop takes the size on its next
   interaction (D6). While mounted, an input sent when the topology shows the
   pane's window at another size than the one last sent re-sends that size
   before the input on the connection (the host writes them to different
   tmux clients, so tmux may apply either first; the redraw follows), at
   most once per `TAKE_INTERVAL_MS` (2 s).

Input: `terminalInput(paneId, bytes)` per §9.5. Never coalesce input with
a delay; send each tap immediately. The one deliberate gap is Send's: the
text goes as a paste, and the CR that submits it follows as keys
`SUBMIT_DELAY_MS` (100 ms) after the paste is acknowledged, so a composer
that reads an Enter inside a fast burst as a newline sees the CR alone.

### 7.6.1 Scrollback paging

A screen-only seed carries nothing above the screen. When the reader scrolls
to the top of the buffer (the page's `onScroll` reports `viewportY === 0` on
the normal screen, throttled to one report per 2 s), the app sends
`OPERATION_REQUEST_TERMINAL_HISTORY` with `terminalHistoryLines` (first page
300 rows, doubling per page to 4,800 — the desktop's numbers) and
`terminalHistorySkipLines` = the scrollback rows the page already holds
(tmux measures from the current display, so rows that scrolled off since the
seed are above it and would come back twice unskipped). The answer is one
`EVENT_KIND_TERMINAL_HISTORY` event: rows joined with CRLF, no trailing
separator, plus `historySize`/`historySizeKnown` (`#{history_size}` from a
targeted probe; false means ask again, not "no scrollback").

xterm has no prepend, so the controller retains every byte handed to xterm
since the seed (the seed included, capped at 4 MB — past the cap paging
stops) and the page rebuilds: `reset()`, write the history rows, one CRLF per
screen row to scroll them fully above the display (the retained seed begins
with `ESC[2J ESC[H`, which erases the display in place), replay the retained
bytes, and `scrollToLine(rowsAdded)` to put the reader back on the row they
were reading. Every page fetched so far is replayed in each splice, topmost
first — the rebuild is whole, so a page left out would be a hole. The reset
is ordered through xterm's write queue (a bare `reset()` would land in the
middle of output still being parsed). Paging latches done when
`skip + rows >= historySize`, when `skip` reaches 10,000 — the host's clamp
and the page's xterm `scrollback`, the same number on purpose — or when
retention overflowed; a request never asks past that limit. Every seed
resets the ledger; once done, retention is dropped. Known imprecision, accepted for v1: rows are spliced
hard-broken (no reflow on resize), and a pane printing during the round trip
can duplicate a few rows — the desktop's anchor/trim machinery is not ported.
Touch: xterm's own touch handling never receives a drag inside this WebView,
so the page converts finger distance to whole rows. Touchmove events are
accumulated at most once per animation frame, retaining fractional rows between
frames. On the normal buffer those rows go to `scrollLines` (one xterm repaint
per visible frame). An alternate buffer has no scrollback, so the page instead
passes synthetic line-mode wheel events through xterm: a TUI that requested
mouse tracking receives its negotiated mouse encoding, and one that did not
receives xterm's cursor-key fallback. The resulting text or binary bytes are
batched into one `TERMINAL_INPUT` per frame, with at most eight wheel events
encoded in any one frame. Stdin is enabled only for that synchronous wheel
dispatch; tapping or typing directly into the WebView still sends nothing.
Finger distance and release velocity use a 2× sensitivity multiplier
so ordinary thumb motion covers terminal history without requiring a fast
flick. Releasing a moving finger continues with a short decaying fling; a new
touch or `touchcancel` stops it. A release more than 80 ms after the last move
does not fling, and a direction reversal resets the velocity estimate so the
fling cannot continue in the old direction.

### 7.7 Terminal output credit

The host will stop sending terminal output once
`terminalOutputWindowBytes` / `terminalOutputWindowRecords` (from
`ServerHello`) of unacknowledged terminal payload are outstanding. Every
`HostEvent` that was charged carries its charge in
`HostEvent.terminalDeliveryBytes` and `HostEvent.terminalDeliveryRecords`:
`TERMINAL_SEED`, `TERMINAL_OUTPUT`, **and** the `PANE_RESOURCE` event a
visibility change admits (`terminal.rs::set_visibility` charges the recovery
bytes; the desktop acknowledges every event's charge in
`bridge.rs::event_delivery_charge`). Acknowledging only seeds and output
would leak one record per hide/show and eventually exhaust the 1024-record
window.

Keep two cumulative counters per connection. After the bytes of an event
have been handed to xterm (or discarded because no terminal is mounted for
that pane — discarded bytes are still charged and still acknowledged), add
the charge and send
`Envelope{ requestId: 0, terminalOutputAck: { connectionEpoch, cumulativeBytes, cumulativeRecords } }`
where `connectionEpoch` is the value sent in this connection's ClientHello
(the host ignores acks carrying any other epoch).
Send an ack at most every 50 ms, or immediately when the un-acked total
exceeds 25 % of `terminalOutputWindowBytes`. Never send an ack larger than
what was actually received (the host rejects it —
`apps/host/src/service/terminal/output_credit.rs`).

Route params are opaque to expo-router. Every `paneId`, `sessionId`, `path`
and `name` handed to `router.push`, `<Redirect>` or `<Link>` goes through
`toRouteParam` (`src/navigation/routeParams.ts`), and every read from

keeps `[A-Za-z0-9_-]` and writes every other UTF-16 unit as `~XXXX`; its
output contains nothing a percent-decode, `URLSearchParams` or path
splitting can change, so it is exact whatever the number of passes.

### 9.4 Workspace — `app/workspace/[sessionId].tsx`

App bar title: session name. List of windows in `index` order, rows 64 dp:

Two action rows above the list (48 dp each, `--chrome-raised`): a folder

mismatch is retried once with the latest `topologyGeneration`.

waits for its acknowledged pane ID, then sends the Settings → Agent command
verbatim plus one newline exactly once. This matches desktop **Run command in
first tab**, so interactive-shell aliases, functions, PATH setup, and version
managers are available. Delivery is scoped to the initiating live connection,
epoch, and server identity and is never retried after a reconnect or timeout.

request timeout; if delivery fails, it reports the partial success and leaves
the terminal visible. The default is `codex`; commands such as `claude` and
their shell options are stored exactly as typed. The hooks on the host pick the
new process up and it appears on the Agents tab.

### 9.5 Terminal — `app/terminal/[paneId].tsx`

The one screen without the standard app bar. Layout:

1. **Header** (48 dp, `--chrome-raised`): centred SVG back arrow; the agent
   mark and the Agents tab's `agentTitle` if an agent routes to this pane,
   else `"{session} · {window}"`; right side: Talk (when an agent is present)
   and `Files` icon buttons → §9.6 rooted at this pane. The mark carries the
   same spinner/dot state as the Agents tab instead of repeating it as text.
2. **Terminal area**: a `WebView` filling the remaining height above the
   input bar, background `--term-bg`. Contents: `webview/terminal/index.html`
   (§10.2).
3. **Key chips row** (40 dp, horizontally scrollable, `--chrome-raised`):
   chips in this order with these labels and bytes:

   | label | bytes sent | with Shift armed |
   | --- | --- | --- |
   | `Esc` | `1b` | `1b` |
   | `⇧` | nothing: arms Shift for the next chip (tap again to disarm) | disarms |
   | `Tab` | `09` | `1b 5b 5a` |
   | `⇧Tab` | `1b 5b 5a` (back-tab; cycles Codex's mode) | same |
   | `Enter` | `0d` | `1b 5b 31 33 3b 32 75` |
   | `⇧Enter` | `1b 5b 31 33 3b 32 75` (CSI-u Shift+Enter, the desktop's constant; a newline in the agent composers) | same |
   | `↑` | `1b 5b 41` | `1b 5b 31 3b 32 41` |
   | `↓` | `1b 5b 42` | `1b 5b 31 3b 32 42` |
   | `Ctrl-C` | `03` | `03` |
   | `Ctrl-D` | `04` | `04` |
   | `y` | `79` | `79` |
   | `n` | `6e` | `6e` |

   Each tap calls `terminalInput(paneId, bytes)` once (`pressChip` in
   `chips.ts` picks the bytes). `⇧` is a one-shot modifier: while armed it is
   drawn as a font-metric-independent SVG in `--accent` with `--accent-ink` and
   `accessibilityState.selected`; the next chip (or Send) disarms it, and a
   chip without a shifted form sends its plain bytes.
4. **Input bar** (56 dp): a single-line text field, placeholder
   `"Type, then Send"`, and a `Send` button (`--accent`). The field is
   plain text: pasting text works, pasting an image or file is ignored
   (Android `contentMimeTypes` left unset; `onReceiveContent` not
   implemented), and the app is not registered as a share target. Send clears
   the field, sends its UTF-8 bytes as one `terminalInput(paneId, bytes,
   { paste: true })`, waits 100 ms after the acknowledgement, then sends `0d`
   as keys (`TerminalController.submitText`). A refused paste sends no `0d`.
   The keyboard's return key is labelled Send and does the same. Empty text +
   Send sends just `0d`, with no delay.

States (shown as a centred overlay on the terminal area, 14 sp `--chrome-dim`):

- attached, no seed yet, < 5 s: nothing (blank terminal).
- no seed after 10 s: `"No output yet. The pane may be idle."`
- `TERMINAL_EXIT` received: banner at the top of the terminal area,
  `--chrome-selected` background: `"This pane has closed."`; input bar
  disabled.
- connection not connected: input bar disabled, chips disabled; the
  connection strip (global) shows above the header.
- pane no longer in topology (window closed elsewhere): replace the
  terminal with `"This terminal no longer exists."` and a `"Back"` button.

Sizing rule (D6): the terminal uses JetBrains Mono at 13 px with
line-height 1.2 (glyph cell ≈ 7.8 × 15.6 px). The WebView measures its
own width and height, computes `cols = floor(width / cellWidth)`,
`rows = floor(height / cellHeight)` (≈ 46 × 40 on a 390 dp phone in
portrait with the keyboard hidden), posts `{ t: "size", cols, rows }` to
RN, and RN sends `resizeTerminal`. xterm is created with exactly those
cols/rows; there is never horizontal scrolling. A pinch gesture is not
supported in v1; landscape is (re-measure → resize). Scrollback is
xterm's default 1000 lines plus whatever the seed carried.

Touch interaction uses one shared terminal-link detector with desktop. A
normal drag scrolls. A tap on an HTTP(S) link opens it in the system browser;
a tap on a supported file-path token resolves it against the exact captured
pane route and opens §9.7. The latter adds no browser, download, upload, or
viewer capability: it can only use the file modes §9.7 already supports. A
450 ms long-press that stays within 8 px selects the word under the finger, or
the whole detected link/path. Two 44 dp handles extend either end and edge-drag
scrolling is available only in the normal buffer. A floating `Copy` action
writes the selection to the system clipboard after the same wrapped-command
cleanup desktop uses. Selection never copies automatically. When a selection
is active, the next terminal tap clears it; a later tap may open a link.

While this screen is open, the desktop's view of the same window is
letterboxed to the phone's size; it snaps back when the desktop is used
(D6). This is expected and is not a bug to report.

Acceptance: opening a blocked Claude Code agent redraws it at phone
width and shows its question within 2 s on Wi-Fi; tapping `y` then `Enter` makes the agent continue and the
pill changes from `Needs you` to `Working` without leaving the screen.

### 9.6 Files — `app/files/[paneId]/index.tsx` and `app/files/[paneId]/dir.tsx?path=`

### 9.7 File viewer — `app/file/[paneId].tsx?path=`

App bar title: file name; subtitle: path relative to root.

The viewer normally receives the pane's browsable active-root capability from
§9.6. A terminal file tap may instead supply an exact-file capability returned
by `RESOLVE_TERMINAL_FILE`; the viewer uses that capability only for the exact
canonical path it accompanied, without replacing or widening the Files
browser's active root.

1. Call `openFileStream(root, rootToken, path)`. The first `fileStream`
   frame for the `operationId` carries `header`. Switch on
   `header.contentKind`:
   - `TEXT` with `contentStreaming === true`: accumulate body frames
     (`data` at `offset`) until the final `response`. Verify total length
     equals `header.totalBytes`. Decode UTF-8 (with replacement).
     - name ends in `.md` / `.markdown` → **Markdown mode**: render in the
       markdown WebView (§10.3). A segmented toggle in the app bar
       `Rendered | Source` switches to plain mode; default Rendered.
     - otherwise → **Plain mode**: monospace 12 sp, `--chrome-ink` on
       `--term-bg`, horizontal scroll, no wrapping, line numbers off.
   - `TOO_LARGE` → placeholder: `"This file is too large to show here ({size})."`
   - `BINARY` → `"This is a binary file."`
   - `IMAGE` → `"Images aren't shown in this version."`
   - `UNSPECIFIED` or missing header → `"Couldn't open this file."`
2. While streaming, show a thin indeterminate progress bar under the app
   bar. Frames for a different `operationId` are ignored.
3. Error response → `"Couldn't open this file: {displayMessage}"` with `"Retry"`.

blocks, tables and task-list checkboxes; links to `http(s)` open in the

   `Locked · tap anywhere to send`), a spinner while `Transcribing…` /
   `Sending…`.
   Disabled (40 % opacity, with the reason under the label) when not
   connected, the agent is gone, or the host is not `ready`. A departed
   agent's pane may remain as a shell, so its presence alone never keeps voice
   input enabled. Presence is rechecked after transcription and again before
   Enter, and both input requests carry an agent guard that the host validates,
   so a confirmed departure cannot submit an in-flight utterance into the
   shell left behind even while its event is still travelling to the phone.

Controller states (`VoiceSession.phase`): `idle` → `recording` (press-in;
any playback stops), optionally → `recordingLocked`, then → `transcribing` (recorder stopped, file read and
deleted, VOICE_TRANSCRIBE in flight) → `sending` (a "you" turn appended,
`TERMINAL_INPUT` of `utf8(transcript)` as a paste, then a `0d` keystroke
after `SUBMIT_DELAY_MS`, the terminal Send's shape, §9.5) → `idle`. Releases
under 300 ms are discarded; an empty transcript toasts `Didn't catch that.`
and sends nothing. Refusals toast per `voiceErrors.ts` (voice-mode-plan.md
§4.6) and re-probe STATUS when the code changes readiness. A
`voice_uv_missing` / `voice_model_missing` / `voice_provisioning` refusal of
STATUS or SESSION is shown as the card's readiness, not toasted. A denied
microphone permission disables the mic with a hint (`recorderError`).
Cancellation passes through `canceling` until the native recorder has stopped,
so another hold cannot race a recorder teardown.

Session lifecycle: the controller is created on the first open and lives in
`voiceRegistry` until End session, across navigation and backgrounding. Screen
focus → `voiceStatus(warm: true)`, `voiceSession(agentId)`, recorder
prepared, and the newest unplayed reply plays. The registration is sent once the host
accepts it, then re-sent every 5 min and on every reconnect (a reconnect to
the same host keeps the sessions; a disconnect or another host disposes
them). A pushed `EVENT_KIND_VOICE_REPLY`
replaces the previous reply's MP3 (`<cache>/voice/<agent>.mp3`; stopping
it if it was playing), appends the reply unplayed, and auto-plays it only
when the screen is focused, the app is active, persisted `voiceAutoPlay` is on,
and the microphone is not listening. A reply received while recording is never
auto-played later; its Play control remains available. Otherwise
it plays on the next focus / foreground. Replies for agents without a
session are ignored. End session sends `voiceSession("")`, deletes the file
and forgets the session; a user disconnect disposes every session locally.
Leaving the Voice screen or backgrounding while a locked take is active
cancels it, deletes its file and releases the microphone.

Agent identity lifecycle is separate from the local Voice-session lifecycle.
The initial agent ID normally becomes the immutable session/controller key; if
that deterministic ID is reused while its retired session is still live, the
new session receives a bounded local suffix instead of overwriting the old
controller. When one ordered Agent State event explicitly retires an
empty-native-ID record and inserts a same-adapter agent with a non-empty native
session ID on the same non-empty pane, the registry deletes the old remote-ID index,
indexes the same controller under the native ID, and updates only the session's
remote `agentId` and route. The screen then reads presence, lifecycle, title,
working state and notification focus from that effective ID while messages and
phase remain under the stable key. Recording, playback, autoplay suppression
and pending work are neither restarted nor replayed. The host performs the
matching bounded registration transfer after durable agent persistence, prunes
dead/expired contenders, queues Agent State, and only then dispatches a Stop
reply. One ingest-order lock prevents concurrent hooks from reversing that
ordinary-path sequence. An independent retirement remains unavailable;
different adapter/pane/server events never promote, and multiple live session
candidates are rejected rather than merged.

Accepted overload limit: if the existing bounded control-event queue is already
full at the exact promotion publication, its normal `RESYNC_REQUIRED` recovery
can replace the Agent State handoff and the local Voice session may become
unavailable. Voice adds no blocking/async priority lane, retry timer, alias
history, or snapshot-based identity inference for this exceptional case.

Reconnect re-registers a session under the promoted ID once the phone has
observed the handoff. A disconnect that overlaps the first native event is a
separate accepted limit: the reconnect snapshot has no retired-ID relationship,
so it cannot retarget a still-local manual-ID session without the rejected alias,
snapshot-inference or protocol state.

Performance: only the `ReplyPlayer` subscribes to `playback` (4 Hz ticks)
and only the card to `hostStatus`; the list re-renders per turn. Nothing in
`features/voice/` other than `voiceRegistry.ts` (pure TypeScript) is imported
until the screen mounts; the recorder, player and file adapter are created
once, on the first render.

## 11. Files protocol details

### 11.1 Streams

`OPEN_FILE_STREAM` answers on the **same request id**: first an `Envelope`
with `fileStream.header`, then zero or more with `fileStream.data`
(`offset` increasing; `eof` on the last), then the `response`. The client
must associate by `requestId` (and double-check `fileStream.operationId`).
The `response` resolves the promise; body frames are delivered to a
per-request sink. `fileStream` frames may interleave with unrelated
events — do not assume they are contiguous.

**File bodies require a bulk connection.** The host classifies
`OPEN_FILE_STREAM` as `Lane::Bulk`
(`apps/host/src/service/requests/operation_policy.rs`) and answers it on the
control connection with `bulk_connection_required: file bodies are allowed
only on an independent bulk connection`. There is no control-lane way to read a
file, so the Files feature opens a second `bridge --stdio` exec channel on
the same SSH session and handshakes it as a bulk lane
(`HostConnection` with the `bulk` option):

- `Envelope{ requestId: 1, clientHello: { bulkConnection: true, expectedServerIdentity: <control serverHello.serverIdentity>, connectionEpoch: <the control connection's epoch> } }`
  and **no** Subscribe (a control operation; refused on a bulk lane).
- The `ServerHello` must pass the §7.3 contract checks and must echo
  `serverIdentity` and `connectionEpoch`; otherwise `failed`. It advertises
  `terminalOutputWindowBytes: 0` — no credit, no events, no terminal.
- Only `OPEN_FILE_STREAM` goes there. `RESOLVE_ACTIVE_ROOT` and
  `LIST_DIRECTORY` stay on the control connection (`Lane::Control`).
- Open it lazily the first time a file is opened; close it on disconnect
  (a reconnect of the control lane changes the epoch, so the bulk lane is
  re-dialled with the new binding).

The phone caps what it will read: if `header.totalBytes > 2 * 1024 * 1024`,
do not read the body — treat it as `TOO_LARGE` locally (still consume
frames until the response arrives so the request id settles).

### 11.2 Active root

`RESOLVE_ACTIVE_ROOT` returns the directory the Explorer should show for a
pane: the pane's current working directory, or the Git worktree root
containing it when `gitWorktree === true`. Pass `knownRootToken` on
re-resolution so the host can answer `rootUnchanged` cheaply. Re-resolve
when the Files screen regains focus (React Navigation `focus` event) and
when an `ACTIVE_ROOT` event arrives for that pane.

## 12. Error handling matrix

| condition | detection | user-visible result |
| --- | --- | --- |
| Host unreachable | ssh `closed` reason `connectFailed` | strip: `"Couldn't reach {host}:{port}."`; auto-retry per §7.2 |
| Auth rejected | `authFailed` | full-screen on `/home`: `"{host} rejected this phone's SSH login. Over Tailscale SSH, check the tailnet's SSH policy; otherwise add the key under Your SSH key to ~/.ssh/authorized_keys on the host."` button `"Your SSH key"` |
| Helper missing | `closed` with `exitCode === 127` | full-screen: `"muxflow-host isn't installed on this host. Install it from the Muxflow desktop app (Settings → Connection)."` |
| Helper prints a usage error / other exit | `exitCode` non-zero, not 127 | strip with the first stderr line; retry per §7.2 |
| Helper incompatible | §7.3 checks | full-screen with the §7.3 message; button `"Reconnect now"` |
| Network drops mid-session | `networkLost` | strip countdown; reconnect; terminals reseed |
| Sequence gap | §7.4 | silent reconnect; log |
| Request timeout | 20 s | toast `"The host didn't answer in time."`; the initiating screen shows its own Retry. Three in a row with 15 s of silence → silent reconnect (§7.5) |
| Host `error` frame, `retryable=false` | §7.4 | toast with `displayMessage`; reconnect |
| Android kills the process despite the service | on next launch, `lastHostId` is set | auto-connect to `lastHostId` on cold start; no notification is lost that was already posted |
| Window at the laptop's size while the phone types | topology snapshot vs the grid last sent (§7.6 step 7) | none; the next input here takes the size back, rate-limited (D6) |

Logging: `console.log` prefixed `[muxflow]`; one always-on, memory-only flight
recorder keeps the newest 1,000 events or 256 KiB, whichever bound is reached
first. It is viewable from the Connection sheet (`"Show log"` text button)
and copyable with a current app/device/session snapshot. No log is persisted or
leaves the phone, and process death clears it.

## 13. Notifications

Channel `agents` (importance HIGH, sound default, vibration default),
created at first launch. Ask for `POST_NOTIFICATIONS` the first time a host
reaches `connected`; if denied, show once on the Agents tab a dismissible
banner `"Notifications are off. You won't hear when an agent needs you."`
with `"Open settings"`.

Decision rule, run for every `AGENT_STATE` event and for every agent in a
reconciling snapshot (port from
`apps/desktop/src/features/agents/notifications.ts::decideAgentNotification`,
simplified to the fields the phone has):

1. Let `prev` be the stored record (may be undefined), `next` the incoming.
2. `attentionAdvanced = prev !== undefined && next.attentionGeneration > prev.attentionGeneration`.
3. `event = attentionAdvanced ? next.attentionKind : (next.lifecycle === "blocked" && prev?.lifecycle !== "blocked" ? "blocked" : undefined)`. If `event` is `""` or undefined → no notification.
4. If `next.attentionGeneration <= notificationWatermark` → no notification (already notified before this connection).
5. If the same `(agentId, attentionGeneration)` was already notified in this process → no notification.
6. If `focusedPaneId === next.route.paneId` and the app is in the foreground → no notification.
7. Otherwise post: title `"{workspace} · {agentTitle}"`, where `agentTitle`
   is the same status-glyph-stripped terminal/task name shown beside the
   agent's status mark (falling back to its assigned or adapter name); body
   `"Needs your input"` for blocked, `"Finished"` for completed; `data`
   `{ agentId, paneId, sessionId, attentionGeneration }`; tag = `agentId`
   (so a newer notification replaces the older one for the same agent).
   Remember `(agentId, attentionGeneration)`.

Tap on a notification: open the app to `/terminal/{paneId}` and call
`agentMarkSeen(agentId, attentionGeneration)`. Dismissing does nothing.
When an agent's `needsAttention` becomes false for any reason (seen on
desktop, retired), cancel its notification by tag.

## 14. Security

- Private key: generated on-device, stored in `EncryptedSharedPreferences`
  (AES-256, Keystore-backed master key), never exported, never logged.
- Host keys: TOFU with an explicit fingerprint dialog (§9.10). Mismatch is
  a hard failure.
- No secret ever appears in the diagnostic recorder. Producers omit user and
  terminal content, and the central sink redacts key bodies and common
  credential/token forms before console or memory receives them.
- The WebViews load only inlined, build-time HTML; `originWhitelist` is
  `['about:blank']` after load; remote content is impossible. Markdown is
  sanitised with the desktop's exact DOMPurify configuration.
- The app never sends clipboard contents anywhere (the desktop protocol
  has a write-only clipboard event; the phone ignores it).
- The connection speaks the host's protocol as a normal client; every
  server-side authorisation boundary (root tokens, expected server
  identity) is respected by passing exactly the tokens the host issued.
- `RECORD_AUDIO` (added by the `expo-audio` config plugin; background
  playback and recording are switched off, so no extra foreground-service
  type) is used only while the Hold-to-talk button is held on the Voice
  screen (§9.11). When prepared, and again immediately before each recording,
  the recorder prefers a connected Bluetooth HFP/SCO microphone, then a wired
  headset (and USB inputs on platforms that enumerate them); unsupported
  devices retain the system-selected route. Android's temporary Bluetooth SCO
  route is cleared after recording so replies return to normal headset
  playback. Recordings are read
  once, sent to the connected host over
  the SSH channel, and deleted; the only audio kept is the newest reply MP3
  under the app cache, removed on End session. No audio goes anywhere else.

## 17. Open questions (answer before M3)

1. **Seed and visibility ordering — answered (M2, live host test).**
   `ATTACH_TERMINAL` alone yields the `TERMINAL_SEED`: `terminal.rs::attach`
   runs with `make_visible = true`, which selects the session, registers the
   pane visible and queues the capture. `SET_TERMINAL_VISIBILITY(true)` after
   it is accepted and emits nothing further (0 additional seeds observed), so
   §7.6 no longer sends it on mount. `visible=false` with empty `data` **is**
   accepted, provided `terminalEpoch` is non-zero (`hide_with_checkpoint`
   refuses epoch 0 with `terminal visibility checkpoint epoch must be
   non-zero`; the phone uses its connection epoch, as the desktop does). The
   empty snapshot means the host cannot buffer the pane, so it releases it
   (`PANE_RESOURCE{ state: RELEASED, requiresSeed: true }`), delivers no
   output while hidden, and reseeds on reveal with the hidden output
   included. Two things the doc had wrong and §7.5/§7.6 now state:
   `RESIZE_TERMINAL` must follow `SELECT_TERMINAL_SESSION`, and the pane id
   of the pane-scoped terminal operations travels in `Request.scope`.
2. **Foreground service type.** `specialUse` is acceptable for a sideloaded
   APK. If the app is ever submitted to Google Play, expect to justify it
   or switch to `dataSync` with its runtime limits.
3. **Two phones / a phone plus a second desktop.** Each is a foreign client
   to the others; `window-size latest` arbitrates. No handling needed, but
   note it in `docs/mobile/qa.md` when testing with two devices.
4. **Attention on open vs. on view.** §9.3.1 marks an agent seen the moment
   its row is tapped. If that feels too eager in use, move the
   `agentMarkSeen` call to "seed rendered" in §7.6 step 1.
